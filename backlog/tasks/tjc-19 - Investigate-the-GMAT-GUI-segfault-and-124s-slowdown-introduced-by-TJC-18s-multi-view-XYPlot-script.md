## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A real manual run this session (the operator launching GMAT-R2026a's interactive GUI directly against a TJC-18-generated CW GUI preview script) exhibited two new, concrete problems not present before TJC-18's multi-view upgrade: (1) the mission run itself took 124.388 seconds (per GmatLog.txt's own reported 'Total Run Time'), up from a sub-second console-mode run of the equivalent numeric script, accompanied by hundreds of repeated 'Error reading file arial.ttf: file not found' / 'courbd.ttf' / 'LiberationMono-Bold.ttf' font-lookup warnings that did not appear before TJC-18; and (2) the GMAT-R2026a process segfaulted on exit ('Segmentation fault ./GMAT-R2026a -r ...'), after 'Mission run completed' and 'GMAT GUI exiting' were already logged, during window teardown. Both symptoms correlate directly with TJC-18's change: the generated script went from one Create OrbitView resource to two Create OrbitView resources (GlobalView, CloseUpView) plus a new Create XYPlot resource (BurnMarkers) with MarkPoint calls, all with ShowPlot = true, i.e. three simultaneous rendering windows instead of one, under this sandbox's software-only (llvmpipe, no real GPU) OpenGL rendering path. This task is diagnosis first: understand whether the segfault is reproducible, isolate which specific element (the second OrbitView, the XYPlot, or the combination/teardown ordering of all three) triggers it, and determine whether it is a fixable defect in how our generated script or src/gmat_verify.py's capture/process-termination code handles multiple simultaneous GMAT GUI windows, or an upstream GMAT/OpenFrames/Mesa limitation under software rendering that can only be documented, not fixed from this repository. This is diagnosis/documentation work, not an automatic mandate to revert or gate TJC-18's multi-view output -- any mitigation (e.g. making the richer output configurable) is explicitly separate, future-decision work, not in this task's scope.

METHOD CORRECTION that invalidates the previous session's central conclusion: 'Mission run completed.' and '===> Total Run Time: %.3lf seconds' are emitted by libGmatBase.so into GMAT's LOG FILE, not onto stdout (confirmed: strings ~/opt/GMAT/R2026a/bin/libGmatBase.so | grep -i 'Total Run Time'). SEGFAULT REPRODUCED (AC1). First clean reproduction: timeout 240s ./GMAT-R2026a -ns -x -l <log> -r artifacts/tjc19_diagnosis/variants/variant_c_full_tjc18.script under a self-managed Xvfb :90, LD_LIBRARY_PATH unset, machine idle (load average 0.07). AC2 ISOLATION -- the segfault is NOT caused by TJC-18's added views; it is pre-existing and intermittent. Per-variant SIGSEGV rate on the idle machine (each trial = one bounded '-x' run, Xvfb, LD_LIBRARY_PATH unset):
- variant A, one OrbitView (pre-TJC-18 baseline): 5/10 SIGSEGV; mission 0.373-0.619s
- variant B, two OrbitViews, no XYPlot: 2/3 SIGSEGV; mission 0.672-0.950s
- variant C, full TJC-18 (two OrbitViews + BurnMarkers XYPlot + MarkPoint): 9/10 SIGSEGV; mission 0.641-1.181s
- variant D, two OrbitViews + XYPlot resource but MarkPoint commands removed: 2/3 SIGSEGV; mission 0.634-0.674s
- variant E, ONE OrbitView + XYPlot + MarkPoint: 3/3 SIGSEGV; mission 0.404-0.433s
- variant F, full TJC-18 script with every ShowPlot = false: 0/3 SIGSEGV, 0 font errors, mission 0.118-0.130s
Conclusion: the pre-TJC-18-style single-OrbitView baseline ALSO segfaults (5/10), so no element TJC-18 added is NECESSARY to trigger it. The one necessary condition found is that at least one plot window is actually opened (ShowPlot = true): variant F, which keeps every resource and command including MarkPoint but opens no window, never crashed. MarkPoint is not necessary either (variant D crashes without it). More simultaneous windows raises the observed rate (1 window ~5/10, 3 windows ~9/10), consistent with a probabilistic teardown race per window rather than a distinct bug introduced by TJC-18.

AC3 -- attempt_gmat_gui_screenshot's capture path is UNAFFECTED, and the reason is now observed rather than reasoned. Probe: artifacts/tjc19_diagnosis/ac3_screenshot_probe.py (log: artifacts/tjc19_diagnosis/logs/ac3_probe.log), run as '.venv/bin/python artifacts/tjc19_diagnosis/ac3_screenshot_probe.py' on the idle machine. It calls the real attempt_gmat_gui_screenshot on all five window-opening variants and, by subclassing subprocess.Popen as src.gmat_verify sees it, records the GMAT child's final returncode (which GMATGUIScreenshotResult deliberately does not expose). All 5 variants: attempted=True, captured=True, non-blank 1024x768 PNG (71953-201359 bytes), elapsed 6.33-6.50s, gmat_returncode=-15 for every run, no leftover GMAT processes. -15 is SIGTERM from the function's own process.terminate(); it never escalated to kill() and never observed -11/SIGSEGV. Mechanism: the function launches '-ns -r <script>' with NO '-x' and kills the process externally after grabbing the window, so GMAT is never asked to run the wxWidgets/OpenFrames window-teardown path where the crash occurs -- it is unaffected because it never reaches that path, not because the underlying defect is absent. Practical consequence: this repo's automated screenshot pipeline (scripts/run_cw_gmat_slice.py, run_rendezvous_workflow) is not at risk from this bug, including with TJC-18's three-window output; only an interactive run that exits normally is.

AC4 -- the 124-second run time did NOT reproduce, and TJC-18's added windows are ruled out as its cause. Mission run time for the full TJC-18 script on an idle machine is 0.64-2.04s across 13 runs, vs 0.37-0.62s for the single-OrbitView baseline: TJC-18's two extra windows cost roughly +0.3 to +1.4s, not +124s. Tested across all four relevant conditions, each with a pre-run idle check: Xvfb/LD_LIBRARY_PATH unset (1.086s, 0.641-1.181s over 10 trials); Xvfb/LD_LIBRARY_PATH set to GMAT's lib (2.041s); inherited WSLg DISPLAY=:0 without LD_LIBRARY_PATH -- the operator's own invocation style -- (0.942s, with the single-OrbitView baseline at 0.540s on the same display). Font-error spam scales exactly linearly with the number of plot windows and is NOT new to TJC-18: 105 lines with one OrbitView, 210 with two OrbitViews or with the full three-window script, 0 with ShowPlot = false. So TJC-18 roughly doubled a pre-existing per-window error spam rather than introducing it. The 124s figure remains unexplained by any script-content factor tested; the previous session's background CPU contention (4 unrelated whole-filesystem find / scans) is the leading remaining hypothesis for the operator's original run, but that is explicitly NOT established here -- it was not measured during the operator's run and cannot be retroactively confirmed.

AC5 / root-cause assessment: UPSTREAM, documented not fixed. The crash is an intermittent use-after-free-style race in GMAT R2026a's own OpenFrames/wxWidgets window teardown under this sandbox's software-only llvmpipe renderer (OpenFrames reports 'llvmpipe (LLVM 21.1.8, 256 bits), Mesa 26.0.3-1ubuntu1'; EGL/zink hardware init fails first with 'failed to get driver name for fd -1' / 'ZINK: failed to choose pdev'). Nothing in this repository is implicated: the crash occurs strictly after 'Mission run completed.', it reproduces identically on the pre-TJC-18 single-OrbitView baseline, it is probabilistic rather than deterministic, and the only lever that eliminates it (ShowPlot = false) also eliminates the visualization that is TJC-18's entire purpose. Corroborating signal: GTK assertion failures appear on stdout immediately before teardown ('gtk_widget_set_size_request: assertion width >= -1 failed' on every variant, plus 'gtk_widget_set_tooltip_text: assertion GTK_IS_WIDGET (widget) failed' on the multi-window variants), i.e. GMAT is already mishandling widget lifetimes before the fatal signal. No fix is available from this repository; per this task's scope, mitigation (e.g. making the richer multi-view output configurable) remains separate future-decision work and was deliberately not attempted. ## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Diagnosis complete; the originally suspected cause is disproven. The segfault is real and now reproducible on demand (exit code 139 after 'Mission run completed.', 9/10 runs of TJC-18's exact script via artifacts/tjc19_diagnosis/run_variant.sh), but it is NOT a TJC-18 regression: the pre-TJC-18-style single-OrbitView baseline segfaults too (5/10). A six-variant isolation ladder shows the only necessary condition is that at least one plot window actually opens -- the full TJC-18 script with every ShowPlot = false keeps all resources and commands (including MarkPoint) and never crashed (0/3), while MarkPoint is unnecessary (variant D crashes without it) and one window suffices (variant E, 3/3). Window count only raises the probability (~5/10 at one window, ~9/10 at three), consistent with a per-window teardown race in GMAT R2026a's own OpenFrames/wxWidgets teardown under software-only llvmpipe rendering, corroborated by GTK widget-lifetime assertion failures preceding the fatal signal. Root cause is upstream; no repository code is implicated and no src/ file was changed.

The 124-second slowdown did NOT reproduce under any tested condition: TJC-18's script runs its mission in 0.64-2.04s vs 0.37-0.62s for the single-view baseline (+0.3 to +1.4s, not +124s), tested across Xvfb and the operator's own inherited WSLg DISPLAY=:0, with and without LD_LIBRARY_PATH, every timing preceded by a recorded idle check (load 0.03-0.16) after the prior session's CPU-contention confound. Its cause remains genuinely unknown and is recorded as such. The font-error spam was also shown to be pre-existing and strictly per-window (105 lines at one window, 210 at two or three, 0 at none), so TJC-18 doubled it rather than introducing it.

AC3 is answered with observed evidence rather than inference: attempt_gmat_gui_screenshot captured a real non-blank window for all five window-opening variants, and the GMAT child's recorded exit status was SIGTERM (-15) every time, never SIGSEGV -- it is unaffected because launching with -r and no -x and then killing the process externally means GMAT is never asked to run the teardown path that crashes. This repo's automated screenshot pipeline is therefore not at risk, including with TJC-18's three-window output; only interactive runs that exit normally are.

Two measurement errors in the prior session's evidence were identified and corrected: 'Total Run Time'/'Mission run completed' are written to GMAT's log file and never to stdout, and a bare -r without -x leaves the GUI event loop running forever, so its EXIT_CODE=124 results meant 'window still open', not 'hang'. There was no hang to explain. Verified with 32 bounded harness runs plus the AC3 probe; 181 tests pass with one pre-existing unrelated failure (tests/test_cw_gmat_slice.py's TJC-3 PNG-size-ordering assertion, failing 3/3 at HEAD independently of this task) and 9 modules uncollectable for pre-existing missing optional deps -- both recorded in the notes as separate work.
