## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TJC-1.21 confirmed that headless GmatConsole-R2026a cannot render OrbitView/OpenFrames graphics in this environment (missing OpenGL/texture plugins), so it substitutes a deterministic SVG line plot as the required trajectory screenshot artifact. The operator has asked for an actual GMAT-rendered GUI screenshot rather than this substitute, and for that artifact to be stored somewhere a user can easily find it rather than only in ephemeral temp/worktree directories. This task investigates whether a real GMAT GUI render is feasible in this environment (for example via a virtual framebuffer such as Xvfb) and, if so, implements it; if genuinely infeasible, it documents the concrete technical blocker as explicit evidence rather than assumption, and ensures the fallback artifact is at least persistently and discoverably stored.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria

- [x] #1 The verification tool attempts a real GMAT GUI (OrbitView/OpenFrames) screenshot capture, for example via a virtual display, before falling back to the deterministic SVG plot

- [x] #3 Whichever artifact is produced (real GMAT render or SVG fallback) is written to a persistent, well-known, discoverable location rather than only a caller-supplied or temp-only output directory

## Implementation Notes

GMAT-R2026a (GUI binary) crashes immediately with 'libEGL warning: failed to get driver name for fd -1' / 'MESA: error: ZINK: failed to choose pdev' under its default GPU path, but succeeds with LIBGL_ALWAYS_SOFTWARE=1 (forces Mesa software/llvmpipe rendering). Ran: env -u WAYLAND_DISPLAY LIBGL_ALWAYS_SOFTWARE=1 DISPLAY=:0 GDK_BACKEND=x11 GMAT-R2026a -ns -r <OrbitView script>. Observed real log output: 'The OrbitView OView has been converted to an OpenFramesInterface object by the libOVtoOFI plugin', 'OpenFrames renderer: llvmpipe...Mesa 26.0.3-1ubuntu1', 'Mission run completed'. Confirmed via python-xlib window-tree walk (pip-installed python-xlib) that real top-level (1100x865) and child (1024x768, 782x502) windows exist with map_state==IsViewable -- a real running GUI, not a crash. However, every external pixel-capture attempt (mss full-display grabs at 3s/6s/15s/20s post-launch waits, and direct X11 XGetImage calls on the specific mapped window IDs) failed: mss grabs returned byte-identical uniformly-blank images (md5 4e9fd36a75989219291d002dd3739145) matching a grab taken with NO GMAT process running at all; XGetImage on window IDs raised BadDrawable/BadMatch X protocol errors. No xwd/scrot/import screenshot utility is installed; apt-get install --dry-run confirms installable candidates exist but sudo is required and 'sudo -n true' fails ('interactive authentication is required') in this shell. Conclusion: this WSLg/XWayland sandbox's compositor does not expose the rendered OpenFrames/OrbitView buffer to standard external X11 screen-capture mechanisms -- a genuine, reproducible, well-evidenced environment limitation, not a GMAT failure.
